# Session control

[English](README.md) | 中文

为 DeepSeek Harness 提供的会话控制。输入框旁的安全暂停按钮会在下一次模型请求发出前停止运行，而不是在流式输出途中直接中止；一个状态条——桌面端锚定在标题栏，浏览器标签页中为悬浮条——可以一次性汇报并控制所有对话。

## 功能说明

**暂停。** 运行进行中时，该按钮会为当前 Session 以及其下所有正在运行的子智能体预约一次暂停：

1. 每个已预约的运行都会保留正在进行的步骤——流式响应及其整个工具调用批次正常结束。
2. 其下一个提议的步骤不会发送给模型：该轮次在此边界处以 `keepInbox` 取消，因此不会发出任何请求，也不会在流式输出中途被截断。
3. 每一轮都会被记录为一次用户停止，因此转录的轮次标题显示为 **已停止 / Stopped**，而不是 **已完成 / Completed**。Session 回到空闲状态，该边界已领取的输入会退回收件箱，排队中的消息或引导文本不会丢失。

暂停只会沿委派树向下生效。暂停子智能体不会预约或停止其父级。

**继续。** 按钮位置保持不变，并变为继续控件（播放图标，主色填充）。点击后会向本次暂停所停止的每个运行各发送一条空的继续回执，每个运行都会基于自己的历史重新唤醒并从中断处继续：已完成的工具结果已在其日志中。从未到达边界的成员只会被取消预约。

真正触发的暂停也会比 DSH 进程活得更久。暂停停止运行的那一刻，宿主会把该 Session 写入 profile 中的账本（`session-control.pauses.json`），因此重启 DSH 后控件仍显示继续，`/pause resume` 也会基于停止时留下的日志打开该 Session 的下一轮。账本记录会在继续本身、`/pause off`，或该 Session 自行开始任意新运行时失效。

如果暂停从未到达边界——因为某个运行自行结束——该暂停会随该运行一起失效。控件会自行清除，而不会假装还有东西可以继续。

### 三种状态

| 状态               | 图标与填充         | 点击动作 |
| ------------------ | ------------------ | -------- |
| 运行中，未暂停     | 暂停图标，中性填充 | 预约暂停 |
| 运行中，已预约暂停 | 暂停图标，主色填充 | 取消暂停 |
| 已暂停             | 播放图标，主色填充 | 继续运行 |

## 暂停子智能体

其在线的父级会通过运行时上下文收到通知。该通知以排队方式送达，不会唤醒父级，并在其下一步生效：

> User paused 2 agents before their next model request: child-1, grandchild. They produce no result until the user resumes them; do not wait for them or re-delegate their work.

该通知会作为来源为 `session-control` 的上下文行被记录，因此父级模型能知道这些子智能体在用户恢复之前不会返回结果。顶层 Session 没有父级，因此不会发出通知。

只有正在运行的智能体会被暂停。空闲的子智能体保持不变，因为预约它会阻止其下一轮——包括用户刚刚发送的消息。

## 监控条

第二个入口是 `shell.overlay`，id 为 `session-control.monitor`，它绘制一个统一的状态条：状态标签和两个批量操作按钮，只有在悬浮部署时才显示拖动手柄。

只有悬浮部署会绘制外框——使用主题的基础背景色、`l3` 细边框和阴影，使状态条看起来像覆盖在页面上的面板。桌面端状态条完全不绘制背景：标题栏行内的实心胶囊会显得像第二层窗口装饰。

悬浮状态条上还有一个齿轮按钮，可打开一项显示设置：毛玻璃效果（`毛玻璃效果`），默认开启。开启时，表面为主题基础色的 72% 透明度，并使用 `backdrop-filter: blur(14px) saturate(1.6)`；关闭时为不透明的基础色。该选项存储在 `dsh.session-control.glass` 中，并同时作用于状态条及其弹出层。

位置取决于部署方式，由仅桌面端预加载脚本写入的 `data-platform` 标记决定：

| 部署方式                           | 状态条                                                                |
| ---------------------------------- | --------------------------------------------------------------------- |
| 桌面应用，Windows                  | 锚定在标题栏行，居中于窗口宽度的黄金分割点（61.8%），无手柄，不可移动 |
| 桌面应用，macOS                    | 锚定在标题栏安全区下方，位置同为黄金分割点，无手柄，不可移动          |
| 浏览器标签页（无 `data-platform`） | 悬浮于顶部，默认位于黄金分割点；只有手柄可拖动                        |

拖动后的位置以框架像素存储在 `dsh.session-control.position` 中，在松开鼠标和窗口大小变化时会被限制在框架范围内，并优先于悬浮默认位置；桌面端状态条会忽略该键，且不会清除它，因此清除该键即可恢复浏览器默认位置。悬浮状态条若被放在下半部分，其面板会向上展开。标签本身只是一个按钮——点击会展开或收起面板——因此拖动操作不会被误认为点击。

标签会优先显示最紧急的信息，排序与 DSH 自身的 Session 行一致：待处理的交互优先于运行中：

| 条件                       | 标签                                    |
| -------------------------- | --------------------------------------- |
| 有对话在等待用户响应       | 琥珀色警告圆点 + `n 个对话在等待你响应` |
| 无等待，有任意对话正在运行 | 旋转指示 + `n 个正在运行的对话`         |
| 无等待/运行，有已暂停的    | 中性空闲圆点 + `n 个已暂停的对话`       |
| 仅剩已完成未查看的         | 绿色完成圆点 + `n 个未查看的对话`       |
| 以上皆无                   | `没有需要关注的对话`，无图标            |

展开标签会按此顺序分组列出：**等待用户响应**、**正在运行**、**已暂停**、**已完成，未查看**；每个对话只出现在其中最紧急的一组。圆点沿用 DSH 共享的 `StateDot` 语义：等待用户响应使用 `warning` 圆点——即 `--dsw-alias-state-warn-primary`（琥珀色 `#f59e0b`），与 DSH 侧栏中「等待审批 / 等待回答 / 计划待审」同一颜色；运行中是加载环，已暂停是中性 `idle` 圆点，已完成未查看是绿色 `done` 圆点。每一行都包含状态圆点、对话标题、已用时间、暂停/继续操作和停止操作；点击标题可打开该对话。面板最高为视口高度的 60%（且不超过 420px），并可滚动。

批量操作会作用于所有对话：全部暂停（当所有运行中的对话都已预约暂停时，会变为全部继续），以及全部停止。全部继续会覆盖所有持有暂停阶段的 Session，包括已被暂停停止的那些——已停止的 Session 不处于运行状态，因此仅限运行中行的继续操作永远无法恢复它们。停止是 Session 控制器自身的取消操作：该轮次以用户停止的方式结束，排队中的输入会被保留。停止按钮使用危险操作样式。

暂停图标是纯粹的竖条，继续图标是纯粹的三角形，与输入框旁的发送和停止圆形按钮风格一致，而不是带环的暂停图案。

已用时间是观察到的运行时长，存储在 `localStorage`（`dsh.session-control.timings`）中，因此页面或插件重新加载后会继续计时同一次运行，而不会从头开始。正在运行的对话从本浏览器首次看到该运行开始时计时；已完成的对话显示该次运行所用的固定时长——即其消耗的时间——而不是距停止过去了多久。如果一次运行的开始和结束都发生在本浏览器未监视期间，则没有时长记录，显示为 `—` 而不是猜测；只有当本页面看到运行处于进行中时，才会关闭时长记录，因此重启不会凭空生成时长。

监控条覆盖顶层对话；子智能体 Session 由其所属的对话负责。它在一个客户端可观察对象中保存暂停记录，该对象与输入框按钮共享，而监控条——它能看到所有 Session——是这些状态转换的唯一写入方。

在模型的最后一步期间预约的暂停可能会输给竞争：运行在到达请求边界之前已经结束，因此什么也没有停止。客户端无法区分这种情况与暂停已实际触发的情况，因此当已预约的运行结束时，监控条会向宿主（`/pause status`）查询，只有确实持有已停止的暂停时才保留继续操作。

已停止的阶段会在两处持久化。浏览器镜像保存在 `localStorage`（`dsh.session-control.pauses`）中，因此页面或插件重新加载后仍会提供继续操作；冷启动时 Session 目录尚未加载完成，这些阶段会被保留，而不会把“尚未列出”误判为“已删除”。宿主的 profile 账本（`session-control.pauses.json`）是持久的那一半：触发暂停的进程不在时，`/pause status` 会从账本回答，这正是继续操作在 DSH 重启后仍然有效的原因。已预约的暂停属于正在进行的运行，既不写入本地存储，也不进入账本；页面刷新后用户需要重新预约。

## `/pause` 命令

按钮驱动的是同一个面向用户的命令，也可以手动输入：

- `/pause` 为正在运行的委派子树预约一次暂停。它是幂等的，在没有运行中的任务时会被拒绝。
- `/pause off` 在暂停触发前取消已预约的暂停。
- `/pause resume` 继续暂停所停止的每个运行；比宿主进程活得更久的暂停会从 profile 账本继续，只有宿主与账本都不持有暂停时才会被拒绝。
- `/pause status` 回答当前智能体是否仍持有使其运行停止的暂停，监控条借此发现模型最后一步抢先完成的暂停；重启后从账本回答。

## 控件

它占据 `conversation.input.activity`，即输入框中模型选择器与停止/发送按钮之间唯一的紧凑位置；在既没有运行也没有可继续的暂停时，它不渲染任何内容。

它复用输入框自身的几何尺寸与材质：34px 圆形，位于该行 -2px 的光学位置；未请求时使用中性的选择器填充，暂停生效后使用主操作的信息色填充。其图标为纯暂停竖条，以及客户端基础组件中共享的实心三角形。两种主题都来自输入框已在使用的同一组 `--dsw-*` 设计令牌。

## 已知限制

- 暂停状态按 profile 持久化：宿主账本让已触发的暂停跨重启保留，客户端镜像让控件跨页面与插件重载保留。仅在客户端内存中预约、尚未到达边界的暂停按设计不持久——它所属的运行已随进程结束。
- 暂停一次性子智能体会将其停在父级的工具调用内部。父级会阻塞在该步骤中，直到子智能体被恢复，因为工具调用未返回时父级无法到达自身的边界。宿主重启后只继续账本中记录的、用户直接操作的那个 Session；已不存在的后代不会继续。
- 父级通知通过 Session id 指代智能体。显示名称保存在子智能体目录中，而暂停路径需要异步读取该目录。
- `conversation.input.activity` 只能容纳一个占用者。启用同样注册在此处的实验性语音输入插件，会替换本控件。
- 监控条的暂停阶段是客户端状态，与输入框按钮共享；宿主账本是其权威来源，一条已失效的镜像阶段会在宿主拒绝继续时自行清除。

## 开发

```sh
pnpm build         # vite: 宿主入口 → lib/index.js，然后客户端入口 → lib/client.js
pnpm typecheck     # 对 src、test 及构建配置执行 tsc
pnpm lint          # oxlint .
pnpm format        # oxfmt .
pnpm test          # 宿主行为 + 构建后客户端产物契约
pnpm check         # typecheck + lint + format:check + build + test
```

源码为 TypeScript。类型检查会把 DSH 包作为普通 `devDependencies` 从 registry 解析，因此仅执行 `pnpm install` 即可在任何检出中完成构建——包括没有 deepseek-harness 目录相邻的 CI。`@deepseek-ai/dsh-*` 包在此仅用于类型：运行时，宿主通过 Cordis 注入提供其服务；浏览器端则从 shell 的平台模块表中获取 `react` 和 `@deepseek-ai/dsh-client-ui-primitives`。

两端均由 Vite 构建。`vite.config.ts` 将宿主入口打包为一个 ESM 文件，Node 内置模块保持外部引用；`vite.client.config.ts` 将客户端入口打包为一个独立的 ES 文件。客户端源码自行注册 shell 的模块加载器工厂，因此其文件顶层唯一的语句就是该注册：React 和基础组件通过工厂的 `require` 获取，经典 JSX 运行时使 `React.createElement` 绑定到同一个 `require("react")`，所有常量和组件都位于工厂闭包内，因为 shell 会把插件 bundle 拼接到共享脚本中。因此无需包装脚本。

格式化使用 oxfmt，即检出自身工具链所用的格式化工具：`.oxfmtrc.json` 仅列出被忽略的路径，因此源码遵循 oxfmt 的默认规则。`format:check` 在 CI 中运行，未格式化的改动会导致构建失败。

代码检查使用 oxlint，即检出自身所用的 linter，它无需额外的解析器包即可解析 TypeScript。插件自带 `.oxlintrc.json`：检出的配置会忽略 `**/*.js` 和 `**/*.mjs`，并且只对 `packages/*/*` 路径应用其严格规则集，因此直接继承它在这里几乎检查不到任何内容。

测试是位于 `test/` 下的 Vitest 文件。宿主用例直接导入 `src/index.ts`，并通过类 Cordis 的上下文驱动它；产物用例在模块加载器契约下执行构建后的 `lib/client.js`，因此 `check` 会先构建再测试。之所以需要 worker-thread 池，是因为 DSH 文件沙箱会阻止默认 fork 池所产生的管道子进程。
